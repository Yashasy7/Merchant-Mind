SECTION 02
Problem Statement

Merchants are data-rich but insight-poor.

Small and medium Paytm merchants generate significant transaction data every day. Yet data alone does not provide actionable intelligence.

❌ Current Reality

  • Merchants generate rich transaction data through Paytm payments
  • Data alone does not surface actionable intelligence
  • Small merchants typically lack analysts, accountants, or marketing staff
  • Business decisions are made by intuition, not data
  • Existing dashboards require merchants to interpret data themselves
  • Inactive customers are not systematically identified or re-engaged
  • Promotions are often based on guesswork with no measurable targeting
  • Financial organization is entirely manual with limited profit visibility
  • Inventory and growth decisions tend to be reactive rather than proactive

✓ What Merchants Actually Need

  • Understand why sales are trending up or down
  • Know which customers are at risk of churning
  • Receive targeted, data-backed growth recommendations
  • Simulate outcomes before committing to a promotion
  • Get a clear picture of monthly profit and expenses
  • Take action on recommendations without needing a team
  • Have a trusted business partner that explains things in plain language
📉

Sales Intelligence Gap

Merchants cannot easily identify peak hours, decline periods, or seasonal patterns without manual analysis.

👥

Customer Blind Spot

At-risk and inactive customers are invisible without systematic tracking. Re-engagement opportunities are missed.

💰

Financial Opacity

Monthly profit, operating margin, and expense anomalies require manual calculation and are rarely understood clearly.

SECTION 10
AI Architecture

LLM vs. Deterministic Backend — Clear Separation

The most critical architectural rule: the LLM explains validated results. It does not calculate financial metrics.

🧠 LLM Responsibilities

  • Natural language understanding and intent detection
  • Business reasoning and problem framing
  • Tool / function selection for orchestration
  • Plan generation for multi-step tasks
  • Explanation of validated backend results
  • Conversational narrative responses
  • Campaign marketing copy generation
  • Anomaly explanation in business context

⚙️ Backend (Deterministic) Responsibilities

  • All revenue, expense, and profit calculations
  • All aggregations and time-series computations
  • Customer segmentation logic
  • Sales trend detection and diagnosis
  • Campaign simulation calculations
  • Revenue forecasting (statistical)
  • Data validation and business rules
  • Expense anomaly detection
Transaction Data (Synthetic)
↓
Python Backend — Deterministic Calculation
↓
Validated Metrics Object
↓
LLM — Narrate + Explain Only
↓
Human-Readable Response to Merchant
🚫
Hard Rule: "The LLM must not blindly calculate or invent important financial metrics. All financial numbers must be computed by deterministic backend code and validated before being passed to the LLM for explanation."
SECTION 11
AI Orchestrator

Tool-Calling Orchestration

The orchestrator receives merchant goals and coordinates tools to produce a structured recommendation.

Orchestration Example: Hero Query

# User: "My sales are falling. Help me increase weekend revenue." # Step 1 — LLM detects intent intent = detect_intent(user_message) # → {type: "growth_recommendation", context: "sales_decline"} # Step 2 — Orchestrator calls tools sequentially sales_data = get_sales_summary(merchant_id, days=14) decline_data = analyze_sales_decline(merchant_id, period=14) segments = get_customer_segments(merchant_id) at_risk = identify_at_risk_customers(merchant_id) # Step 3 — Generate recommendation (deterministic backend) recommendation = generate_growth_recommendation( sales_data=sales_data, decline=decline_data, customers=at_risk, goal="increase_evening_revenue" ) # Step 4 — LLM explains validated result (no inventing numbers) response = llm_explain(recommendation, tone="merchant-friendly") return {"recommendation": recommendation, "explanation": response}

Available Tools / Functions

get_sales_summary(merchant_id, days)MVP
Returns aggregated revenue, transaction count, avg value, trend for period.
analyze_sales_decline(merchant_id, period)MVP
Detects decline magnitude, affected time windows, calculates % change per bucket.
get_customer_segments(merchant_id)MVP
Returns customer counts per segment (VIP / Loyal / New / At-Risk / Inactive).
identify_at_risk_customers(merchant_id)MVP
Returns list of at-risk + inactive customers with recency and value data.
get_business_health(merchant_id)MVP
Returns overall health score, key strengths, concerns, top opportunity.
generate_growth_recommendation(sales, customers, goal)MVP
Produces structured recommendation: target, offer, timing, reasoning, impact.
simulate_campaign(strategy, target_segment)MVP
Deterministic what-if calculation. Returns projected transactions, revenue, cost, ROI.
create_campaign(approved_recommendation)MVP
Creates campaign record after merchant approval. Simulates execution + result.
get_profit_loss(merchant_id, month)MVP
Deterministic P&L: revenue, expenses, operating profit, margin, category breakdown.
get_expense_summary(merchant_id, month)MVP
Returns expense by category, anomaly flags, comparison vs. prior month.
forecast_revenue(merchant_id, horizon)Simplified
Statistical rolling-average forecast. Returns range estimate with trend explanation.
get_campaign_result(campaign_id)MVP
Returns simulated campaign performance: transactions, revenue, customer response rate.

SECTION 19
Fallback Strategy

Emergency Fallback Plans

The demo must never fail due to an external service. Every dependency has a fallback.

🔴 LLM API Fails / Slow

  • Use deterministic intent routing in orchestrator
  • Return pre-validated structured response objects
  • Pre-written explanation templates per intent type
  • Copilot still shows correct backend data with template text

🔴 PostgreSQL Fails

  • Pre-load demo data into memory (Python dict/Pandas DataFrames)
  • All services have an in-memory data mode flag
  • JSON fallback files in data/fallback/
  • Switch mode via env var: DATA_MODE=memory

🟡 Campaign API Unavailable

  • Simulated campaign execution (already planned from day 1)
  • Result generated deterministically
  • Status shows "SIMULATED" badge clearly in UI

🟡 ML Clustering Fails

  • Fall back to deterministic rule-based segmentation
  • customer_service.py needs no scikit-learn for rules mode
  • Same 5 segments produced — no visible difference in demo

🟡 Chat Integration Breaks

  • Use suggested prompts that trigger pre-wired backend calls
  • Copilot renders as structured Q&A flow
  • Backend analytics still run; result cards displayed directly

🟢 Time Runs Short

  • Drop: Forecasting screen, advanced ML, secondary animations
  • Simplify: Customer screen to static data display
  • Keep: Hero growth workflow, Copilot, Approval, Accountant
  • A working 6-screen demo beats a broken 12-screen demo

Security & Trust

Security Principles for MVP

Backend Security

  • Input validation: All inputs validated via Pydantic schemas before processing
  • SQL injection prevention: SQLAlchemy ORM (parameterized queries only)
  • LLM context filtering: Only validated business metrics passed to LLM; no raw user data
  • Output validation: LLM responses validated against expected schema before returning
  • Environment secrets: API keys via env vars only; never hardcoded
  • CORS: Origin whitelist enforced in FastAPI middleware
  • Audit logging: Campaign approvals + rejections logged with timestamp
